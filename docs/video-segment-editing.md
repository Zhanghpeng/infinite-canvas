# 视频分段编辑：长片角色替换与局部重绘

> 两个场景共用一条链路：**切分 → 逐段生成 → 合成**。
> 差别只在参考图怎么给。本文记录设计方案、关键取舍与已知边界。

## 1. 需求与约束

| 场景 | 用户想要 | 现实约束 |
| --- | --- | --- |
| 长视频角色替换 | 3 分钟片子里的人物换成新角色，多角色，剧情节奏不变 | 主流视频模型单次只能出 5–10 秒，吃不了长片 |
| 局部重绘 | 15 秒片子只有 10–15 秒有瑕疵，只重画这段，接缝不能看出来 | 模型无法"续写"，只能整段重生成 |

两条约束指向同一个解法：**把长片切成模型吃得下的段，逐段生成，再按原时间轴拼回去**。
真正难的不是切，是**接缝**：接缝处不能跳、不能糊、不能有风格断裂。

## 2. 视频节点新增了什么

### 2.1 数据模型（`web/src/types/canvas.ts`）

```ts
// 这个节点是源视频里的一段
type CanvasVideoSegment = {
    sourceNodeId: string;        // 源视频节点
    sourceDurationMs?: number;
    startMs: number;             // 在源片中的区间，左闭右开
    endMs: number;
    index: number;               // 拼接顺序
    sceneStart?: boolean;        // 首帧是否落在场景切点上（决定要不要淡化）
    mode: "repaint" | "character-swap";
    anchor?: { firstFrameMs?: number; lastFrameMs?: number };
    /** 这一段实际生效的角色图节点；空 = 跟随全局。单段重试按同一套参考重来。 */
    castNodeIds?: string[];
    /** 生成时长与目标差超过 500ms 时记录：合成已归一化，但内容可能不完整。 */
    durationDriftMs?: number;
};

// 这个节点是切出来喂给模型的参考片段（中间产物，不进拼接）
type CanvasReferenceClip = {
    sourceNodeId: string;
    startMs: number;
    endMs: number;
};

// 这个节点是拼出来的成片
type CanvasVideoComposite = {
    partNodeIds: string[];
    crossfadeMs: number;
    sourceNodeId?: string;
};
```

**段即节点**，不是隐藏在某个弹窗里的内部状态。这样每段都能单独预览、单独重试、
单独再开一次时间轴继续修 —— 符合画布"万物皆节点"的心智，也省掉一套自定义列表 UI。

节点左上角有徽章：段是靛蓝色「第 N 段 · 00:03.2–00:08.4」，成片是绿色「N 段拼接」，
参考片段是灰色「参考片段 · 时间码」，时长偏差是琥珀色。画布上并排躺着十几个视频时，
靠标题认太慢。

### 2.2 入口

视频节点悬浮工具栏 →「分段处理」（剪刀图标），打开时间轴工作台。

## 3. 局部重绘：无缝靠三件事

### 3.1 只把问题区间送去生成

时间轴上拖出 `[10s, 15s]`，其余画面**原样保留**，从根上避免"整片重生成导致其它地方又变了"。

保留这件事是本功能的关键。生成出来的几秒只是一块补丁，用户要的是完整的 15 秒，
所以合成时按 `保留头 [0, 选区起点] + 重绘段… + 保留尾 [选区终点, 全片]` 组装：

```
原片       ├──────────────15s──────────────┤
选区                    ├──5s──┤
送去生成                 ▲      ▲  两端各钉一帧
成片  =   保留(0–10s)  +  重绘(10–15s)  +  保留(15s–15s, 空)
```

只把重绘段拼起来的话，用户拿到的是"10–15 秒那 5 秒"，不是他要的整条片子 ——
这是纯合成逻辑的问题，跟模型能力无关。

### 3.2 首尾帧钉死在原片上（仅局部重绘）

选区两端各抽一帧，作为参考图的前两张传给模型：

```
参考图 = [角色图…, 本段起始帧, 本段结束帧]
参考视频 = 原片的本段
```

这一段的开头必须接住前 10 秒的最后一帧，结尾必须接住 15 秒之后的第一帧。
两端都钉在原片的真实帧上，中间交给模型自由重绘 —— **接缝落在同一帧上，本来就连着**。

这里有个取舍要说清楚：ComfyUI 的 `frame`（首尾帧）模式**不接受参考视频**，
`omni`（全能参考）模式**不接受首尾帧槽位**，两者互斥。我们选 `omni`，
把首尾帧当普通参考图传 —— 因为"看到整段内容与节奏"比"两帧硬约束"更重要：
只给两帧，模型会把这 5 秒重画成完全不同的内容，再准的接缝也救不回来。

**角色替换不送首尾帧** —— 这条边界是踩出来的。局部重绘要保留原人物，两张原片帧
只用来钉接缝，是加分项；角色替换正好相反：那两帧里的正是**要被换掉的旧人物**，
作为 `ref_image` 排在角色图后面，模型会把它们读成额外的人物参考。表现就是
"换不干净、原人物残留"，而且提示词里说得再清楚也压不住 —— 它是图生图，图的权重高于文字。

所以 `runVideoSegment` 按模式分派：

| 处理方式 | 工作流 | 首尾帧 | 送法 |
| --- | --- | --- | --- |
| 局部重绘 | omni | 送 | 追加进参考图（`ref_image_0N+1/0N+2`） |
| 局部重绘 | frameVideo | 送 | `first_frame` / `last_frame` 槽位 |
| 角色替换 | omni（默认） | **不送** | — |
| 角色替换 | frameVideo | 送 | 槽位（入口本来就拦了，见 7.2） |

弹窗「输出规格」里如实写着这一批送不送参考帧，用户在提交前就能核对。

### 3.3 非切点边界做短交叉淡化

段边界如果不在场景切点上（比如为了卡 6 秒上限而硬切的），合成时把后段开头与前段
末尾几帧混合（默认 3 帧，约 0.1 秒）。够吃掉模型首尾的细微色差与运动差异，
又短到肉眼看不出糊。边界正好是硬切时**不做**淡化 —— 那里本来就没有连续性，淡化反而拖影。

淡化必须**不改变总时长**。一开始实现成"重叠消耗"式淡化（前段尾巴与后段开头合成一组帧），
每道接缝少掉 3 帧。单看一遍没问题，但音轨是整轨取自原片的：

| 段数 | 接缝 | 画面比音轨短 | 表现 |
| --- | --- | --- | --- |
| 2 段 | 1 | 0.1s | 看不出来 |
| 10 段 | 9 | 0.9s | 越到后面口型越对不上 |

所以改成「定格式淡化」：前段帧一帧不丢，后段开头几帧与**刚刚发出**的前段尾帧混合，
alpha 从 1/n 递增到 1。因为接缝两侧本来就应该几乎是同一画面，这层"残影"看不出来；
换来的是画面与音轨严格同长，长片拼十段也不会漂。

## 4. 角色替换：分段 + 角色绑定

### 4.1 分段策略（`planSegments`）

边界优先落在场景切点上，段长围绕**目标段长**浮动，并夹在模型能力区间内 —— 这个区间
不是审美偏好，是**模型接口的能力边界**：MiniMax 系（海螺 / H3 reference-to-video）
只接受 5–15 秒的参考视频。所以 `resolveSegmentLimits()` 从渠道 id、工作流 id/名称、
模型名里认出渠道，默认给 5–15 秒；认不出时退回保守的 1.2–6 秒。

**目标段长的默认值由画面自己决定**（`recommendSegmentTarget`）：取相邻切点差的中位数
（首尾两个镜头也算在内），再夹进能力区间。镜头中位数 6 秒的片子就一段一镜头；中位数
短于下限（快切片）只能合并，此时取下限，跨最少的镜头；长于上限（长镜头）取上限，交给
均分。弹窗里的「目标段长」可以覆盖它 —— 调大等于允许一段横跨多个镜头，换更少的段数。

落刀规则（`planBoundary`），按优先级三档：

1. `[起点+下限, 起点+上限]` 里有镜头边界 → 取离目标段长**最近**的那个。窗口下沿是下限，
   每段都合法；上沿是上限，永远不超模型能力；
2. 没有镜头边界、剩余又放得下 → 直接收尾，不把一段完整画面从中间劈开；
3. 没有镜头边界、剩余放不下 → 按目标段长落刀，夹在窗口内。

> 早期版本取的是窗口内**最远**的切点，等于把每段塞到逼近上限：单段上限 15 秒时，
> 一段常常横跨三四个镜头，接缝落在镜头正中 —— 模型要在同一段里同时照顾两个场景，
> 重绘出来两头都对不上。改成"离目标最近的切点"后，快切片贴着下限、慢节奏片子一段
> 一镜头，段边界全部落在真实硬切上，合成时大部分段根本不需要淡化。

场景检测只认画面变化，产出的段长完全不受模型约束：一段 0.8 秒的闪白、一段 22 秒的
固定镜头都会原样冒出来。前者提交必被拒，后者被截断且用户不知道。所以
`fitRangesToLimits()` 在规划阶段就修掉：

1. 短于下限的段并入前一段（**不判断合并后是否超上限** —— 否则会留下"并了超限、
   不并又不合规"的短段，两边都不成立；
2. 超过上限的段按上限均分。均分天然满足下限：上限是下限 3 倍时，每份都 > 上限/2。
   均分出来的后半段不再标 `sceneStart`，它起于画面正中，本来就没有连续性要求。

一个切点都检测不出时（整片一个长镜头）目标段长会落到上限，按上限均分。场景切点用稀疏采样检测：每 250ms 抽一帧压成 32×18 的
**RGB 三通道**签名，相邻帧平均绝对差超过 0.22 就算切点，400ms 内的重复切点只留分数最高的。

> 踩过的坑：一开始只算亮度，红切蓝这种"同亮度、反色相"的转场差只有 0.157，
> 低于阈值被漏掉，段就切在画面中间了。改成三通道后红蓝差 0.52，稳定检出。

下发的 `seconds` 也夹到同一区间：短于下限的段（整片本来就很短）按下限请求，
合成层再按目标时长裁回去 —— 这是"宁可超生成再裁"的兜底，不是正常路径。

### 4.2 角色绑定（逐段）

切点只能算出"画面变了"，算不出"这一段里有几个人"。一段双人对白后面接一个女主特写，
把两个角色的参考图同时喂给两个段，模型会在特写里也把第二个人画出来 ——
这正是"超分了好多人物"的来源。

所以角色绑定是**分段的**：`SegmentPlan.castNodeIds` 覆盖全局集合，
空数组是有效语义（这段没有要换的人），因此下游判 `!== undefined` 而不是判长度，
否则"这段不挂角色"会静默回退成全局角色。

UI 侧配套两件事：段卡上直接显示这段挂的头像；右侧面板点段即可改。
段边界一变（改单段上限、切模式、拖选区），按序号的覆盖会错位，此时**清空覆盖**
并让用户重配 —— 挑角色花的是人的判断力，宁可重来也不能静默换成别人。

同一段里有多个角色时仍靠顺序对应，见第 6 节。

### 4.3 与局部重绘的唯一差别

| | 局部重绘 | 角色替换 |
| --- | --- | --- |
| 处理范围 | 用户选区 | 全片 |
| 参考图 | 首尾帧 | 仅角色图（**不送首尾帧**，见 3.2） |
| 保留原画 | 选区外全部 | 无（整片重生成） |

角色替换的参考图只有角色图这一种，顺序就是模型看到的 `ref_image_01..0N`：
**提示词里写的"参考图 1"必须是用户勾的第一个**。所以选择顺序不做任何排序，
弹窗的缩略图角标直接标序号，避免"我以为图 1 是女主"这类错位。

### 4.4 提示词按人数分档

人数是提示词里必须写清的一件事：单人段套双人模板，模型会凭空再画一个人；
双人段套单人模板，第二个人会被抹掉。而这两种错模型**都不会报**，只会安静地
多画或少画一个人 —— 等到成片里才发现，前面的段已经白跑了。

所以档位规则抽成纯函数 `promptTemplateKey(count)`（`one` / `two` / `many`，0 返回 null），
弹窗填默认值、提交前兜底都走它：

- 勾选角色后自动填入对应人数的模板（`promptTemplate.one/two/many`）；
- 用户改过的提示词不被覆盖（`autoTemplate` 记着上一次自动填入的原文），
  但人数与勾选对不上时会显示「按 N 个角色重填」；
- 段级角色数与全局不同时，这一段的提示词自动按段人数套模板 ——
  沿用全局那句"两个人"会把这一段写坏。用户自己写过的段级要求不替换，只提示；
- 提示词被清空时，提交侧的兜底也按人数取模板，不退化成"把人物替换成参考图中的角色"
  这种没交代人数的说明文字。

**自动填入的模板只是起点，用户改完可以存为自己的默认**（`lib/canvas/prompt-template-store.ts`）：

- 存的位置是 `localStorage`，key 按**精确人数**分（`…:character:<count>`），不按档位。
  原因：正文里写死了人数与参考图编号（"参考图 1 至参考图 N"），3 人存的那份拿去给
  5 人用，数字就是错的 —— 而这种错模型不会报，只会少画两个人。换了人数就该回到内置
  措辞，宁可重填一次，也不复用一个数字不对的版本。
- 存完之后把 `autoTemplate` 的基准换成这份，否则"是否改动过"永远算成改过，
  每勾一次角色都弹一次"人数对不上，要不要重填"。
- 「恢复内置」会连带删掉这份自定义，不然下次打开又填回来，看着像没生效。
- 存储不可用（隐私模式）时不装作存好了：明确提示"这次修改照样生效，只是下次要重改"。



## 5. 合成：为什么重编码而不是拼压缩包

段可能来自不同模型、不同分辨率。直接拼 MP4 压缩包会遇到 SPS/PPS 参数不一致，
表现为花屏或后半段解码失败。所以统一走「解码 → canvas 统一尺寸 → 重编码」：

- 参数一致，接缝干净
- 可以在 canvas 上做交叉淡化
- 分辨率不一致时段按 contain 缩放，不变形

代价是耗时（1080p / 15 秒约数秒），有进度百分比。

**音轨整轨取自原片**，不拼接各段的音频。局部重绘只改画面，声音本来就该是原声；
角色替换要"节奏不变"，保留原声也最稳妥。副产品是音频永远不会出现接缝。

配套约束：正因为音轨是整条连续的，**画面也一帧都不能少**。这就是 3.3 里淡化不能丢帧、
以及保留段必须补回的全部理由 —— 音画是两条必须逐帧对齐的轨道，少一帧就漂到片尾。

### 5.1 一个必须显式给区间的坑

无损切分出来的文件带着 MP4 的 edit list：文件里存了「上一个关键帧 → 切点」这段多余数据，
元数据声明从第 N 秒开始播。播放器会按元数据裁，所以观看正确；
但 `VideoSampleSink.samples()` 顺着原始时间戳解码，会把这段多余数据也读出来。

实测：切 `[1s, 3s]` 得到 probe 2000ms 的文件，解码却有 90 帧 / 3.0 秒。
拼接两段于是得到 6 秒而不是 4 秒。

修复：合成时每段都显式传 `startMs` / `endMs`（缺省用 `probeVideo` 的时长），
不依赖文件自带的 edit list。

## 6. 已知边界

1. **角色与人物的对应靠顺序 + 提示词**，没有面部识别或框选绑定。
   同一段里两个角色交叉走动时可能串脸。下一步可以做成「在某一帧上框选人物 → 绑定角色」，
   再喂给支持区域约束的工作流。
2. **首尾帧是软约束，且角色替换不用它**。原因见 3.2：`frame` 与 `omni` 互斥，
   而角色替换还要额外回避"原片帧里是旧人物"这个污染源 —— 所以接缝精度
   完全靠参考视频本身 + 合成层的定格式淡化兜住。如果渠道里配了只吃首尾帧的工作流，
   可以走严格模式，但那会丢掉内容参考。
3. **参考视频头部会多看 ≤2 秒**（edit list 残留的 GOP）。同一镜头内无害，
   跨镜头时模型可能多看到上一镜的尾巴。
4. **合成是重编码**，不是无损拼接。段数很多时可考虑同参数段的 remux 快路径。
5. **场景检测是稀疏采样**，瞬闪、极短镜头（< 250ms）会漏。漏了也只是分段位置不理想，
   用户可以手动拖选区。
6. **段内参考图只能从画布已有的图片节点里选**，弹窗里不能现场上传或从某一帧上框选人物。
   要新的角色参考图，先在画布上生成/拖入一张。下一步可以做"在段卡的三帧上框选人物 →
   自动裁成参考图 → 直接挂到这一段"，那才是真正的手动精确控制。
6. **需要 WebCodecs**。Chrome / Edge 现代版、Safari 15.4+ 可用；
   不支持时入口会直接提示，而不是跑到一半失败。
7. **角色替换目前整片都会重绘**，成片完全由模型输出构成，
   原片只作为参考（内容 + 节奏）。想"只换某几秒的人"应改用局部重绘模式。
8. **音轨长度由 AAC 帧对齐决定**，实测比画面长 10ms 量级（一个 AAC 帧 21ms），
   播放器感知不到，无需处理。
9. **模型区间是认出来的，不是问出来的**。`resolveSegmentLimits` 靠名字匹配
   （minimax / hailuo / 海螺 / referencetovideo），新渠道上线不会自动带上正确区间。
   哪天接了第二个吃 5–15s 的渠道，把它的关键字加进去即可。

## 7. 交互流程

```
视频节点 → 工具栏「分段处理」
  ↓
时间轴工作台（打开即分析：抽帧带 + 场景切点，带进度）
  ↓
[局部重绘]  时间轴拖选区 → 两端自动吸到切点 → 看到首/尾锚定帧缩略图
[角色替换]  切到角色模式 → 全片自动分段 → 下方铺出分段轨道
  ↓
先选全局角色（大多数段用它）→ 再点个别段单独改：
  主预览循环播这一段 → 三帧看出段里有谁 → 只勾这张脸 → 可配段级提示词
  ↓
写要求（留空用默认模板）→ 调目标段长（默认按镜头长度推荐，通常一段一镜头）/ 淡化帧 / 是否保留音轨
  ↓
生成：逐段建节点（先建后填，失败也能定位是哪一段）
  不必等全部段配完 —— 配好一段就能先跑一段，剩下的随时接上（见 7.2）
  ↓
[局部重绘] 补回选区外的原画 → 合成成片，总时长与原片一致
[角色替换] 全部段拼接 → 合成成片
  ↓
每段都可单独重试、单独再开时间轴继续修
```

段节点先以 loading 态落到画布再开始生成，长任务中途能看见进度落在哪个节点上。
一段失败就停 —— 继续只会产出一堆接不上的碎片。

### 7.1 画布铺排：一批读起来是一条数据流

**点下提交的一瞬间，这一拨的段位就全部铺到画布上**（排队态），而不是"轮到哪一段才建哪个节点"。
后者的问题很具体：弹窗已经关掉，画布上什么都没有，用户只能盯着一片空白等第一段切完 ——
既不知道点了有没有生效，也不知道这一批到底有多少段。现在点完立刻是一整列
「第 N 段 · 排队中」，轮到谁谁转起来。**排队批同样如此**：哪怕它得等上一批跑完，
点完也立刻有节点，用户看得见"排在哪"。

段节点在画布上以源片为基准向右铺两列：

```
源片 →（+96）参考片段列（≤360px，小一号）→（+96）生成段列 →（+96）成片
```

- **排队/运行/已完成三态可辨**：排队是静止的虚线圈 + 「排队中」，跑起来才转；
  十个节点长得一样的话，用户看不出哪一个真的在跑。段节点在 loading 态也带
  「第 N 段」徽章 —— 否则一列转圈谁是谁都分不清。
- 每段一行，源片向每个段节点拉 lineage 连线；参考片段刻意不连线 ——
  它是中间产物，三条线会把画布织成网，徽章和元数据里的 `sourceNodeId` 已说清来源。
- **行高按实际节点高度重排**，不是按源片高度。预铺时按源片高度留位，但模型经常吐
  竖屏（544×960），段节点生成后比源片高近一倍 —— 这一段一变高，就把后面**还在排队**的
  段整体下推差额。已经出画面的段不动（用户可能手动拖过，不能替他搬）。
  段生成完被缩放时，参考片段会重新垂直居中到该段上。
- **同一个源片跑第二批时整列右移**：不移的话新段直接压在上一次的节点上，
  画布上出现两个"第 1 段"，谁对谁错只能靠猜。
- 成片列宽按实际最宽的段算，竖屏批次的成片不会离段老远。
- 视口跟着走：铺完立刻把「源片 + 整列段」带入视野（用户刚点的提交，这一下必须让他
  看见东西在长出来）；收尾时再按实际大小适配一次 —— 但**整批都在屏幕外才拉回**，
  用户已滑去看别处干活时不抢视角。
- **一段失败后，后面没轮到的段标成「未生成」**，不留着转圈。转圈停不下来是最容易
  被当成"卡死"的观感，标清楚这批跑到第几段就一目了然。

### 7.2 断点续跑与分批提交

**提交不要求整片配完。** 逐段配角色是慢活（一段段看画面、点人头），生成更慢；
把两者强行串起来，用户得先花五分钟配完再干等二十分钟。现在：

- 底部按钮按当前可跑的段数变文案：「生成 10 个段」⇄「先生成已配好的 3 段」；
- 没配角色的段**不拦提交**，只在按钮左边说明「还有 7 段没配角色，这次先跑 3 段」；
- 只有"一段都跑不了"时才禁用（提示先选全局角色或点开某段挑一张）。

分批状态记在内存里（刷新页面任务本身也没了，续跑无从谈起）。重开该源片的时间轴：

- 顶部横幅说明「这批已完成 x/y 段，还有 z 段没跑」；
- **切段参数与逐段配置按时间区间复原**（`restore` / `casts`）。不复原的话重开等于重新分段，
  目标段长回到默认值、边界全变，段级角色作废 —— 用户配了半天的东西全白费；
- 已生成的段在段卡上打绿标「已生成」，提交时**整段跳过** —— 节点和参考片段都在画布上，
  重跑只会多出一批重复节点；
- 提交时若判定与上一批**分段边界完全一致**（`sameRangeBoundaries`），接在那一批里跑：
  复用列坐标、已产出的段和行光标，新段接在原列底部，全齐了才合成。边界不一致说明用户
  重切了段，另起一批（整列右移），不硬接。

生成期间又点一次提交（上一批还没跑完）：**先铺节点，再进队列**。这一点很关键 ——
队列里排着的批同样在提交瞬间把段节点铺到画布上（排队态），只是暂时不执行。
早先的实现只把 plan 塞进 `queuedVideoPlansRef` 就 `return`，画布上什么都不出现，
用户看到的是「第一段在跑、第二段毫无反应」，很自然会以为第二段没提交上 ——
而实际上它已经排着了，只是没有任何可见证据。

现在的口径：

- 排队批的节点和正式批长得一样（「第 N 段 · 排队中」），区别只在它得等前一批收尾才被点亮；
- 队列存的是**已铺好节点的那一批**（`PreparedVideoBatch`），不是裸 plan。轮到它时只差执行 ——
  再走一遍提交会重复铺节点；
- 每批一个 `AbortController`：取消当前批不会顺手把队列里的下一批也停掉；
- 队列执行前会**重排本批还在排队的段**（按同批已完成/正在跑的节点最低边往下接）。
  预铺时算的行号到这时候早就失效了 —— 前一批的段生成后可能变高被下推过，用户也可能
  手动拖过节点，不重排就是两段叠在一起；
- 队列是 FIFO，可以排多批；`pendingVideoBatchRef` 只在清自己那一份时才删
  （身份比较），否则前一批跑完会把排队批的断点记录一起抹掉。

「可跑」的判据是 `isSegmentRunnable`：局部重绘永远可跑；角色替换要求生效的角色集合非空，
**显式给过的空数组也算可跑**（"这段确定不换人"，比如纯空镜，用户就是要它按原样重画）。

### 7.3 工作台：段是第一等公民

弹窗不是"一张表单"，而是"一排段 + 一个属性面板"。左边从上到下是
**预览 → 时间轴 → 分段轨道**，右边是**全局设置 ⇄ 选中段的设置**。

分段轨道每段一张卡，横向铺开：

```
┌ 第 2 段 ─── 5.2s ┐   ← 三帧拼条（起点 / 中段 / 尾帧）+ 合规标
│ [起][中][尾]      │   ← 绿勾 = 落在 5–15s，红叹 = 超出
│ 00:03.2–00:08.4  │
│ (头像)(头像) 已自定义 │
└──────────────────┘
```

点一张卡：主预览**循环播这一段**，右栏切换到这一段 —— 角色勾选（带名字，
3 列大图，不是 24px 小圆点）、段级提示词、"跟随全局"、"应用到全部段"。

为什么要三帧而不是一帧：判断"这段里有几个人、角色站在哪一侧"是挑参考图的前提，
只给起点一帧时这个判断做不了，用户只能整批试错。三帧横拼正好覆盖段内首中尾。
抽帧走 `buildSegmentStrips()`：一次 load 视频串行 seek，按段边界做缓存，
改角色不会触发重新解码。

两条与"精确"直接相关的口径：

- **段卡上的红色时长徽章不是装饰**。超出模型区间时提交不会被拦（短源片也得能用），
  但会明确告诉用户"按下限请求、成片按原长裁切，画面可能偏静" ——
  静默给一个变慢的成片，比报错更难发现。
- **段级覆盖按序号存，边界一变就清空**。理由见 4.2。

选中段后右栏底部有两个动作：**重播这一段**、**生成第 N 段**。单段入口不是为了省额度，
而是因为角色替换的常态是"改一段、验一段"—— 底部整批按钮跑的是所有配好的段，
改完第 3 段想立刻看效果时，它会连带把没验过的段一起烧掉。

已生成的段**不放行**单段生成，按钮会变成禁用并指路"右键画布上的段节点重跑"。
原因：单段重跑走的是节点重试链路，它只更新段节点，成片要等整批跑完才重合成；
从弹窗里直接点会得到"段更新了、成片还是旧的"这种半成品，比没有入口更难受。

### 7.4 生成参数：从节点继承，不从全局

分段链路的生成参数一律**从源节点推导**（`buildSegmentConfig`），这是踩过坑之后定下的口径。

原来这里只搬了 `channelId` / `workflowId` 两项，其余全部落在全局配置上。后果是：
用户在视频节点上明明选了 960×544 横屏 + 某个全能参考工作流，跑出来却是一列
**544×960 竖屏段** —— 因为全局 `size` 是 `auto`，而 ComfyUI 的兜底值就是竖屏。
用户的结论只有一句："我选的参数没生效。"

现在的取值顺序：

| 参数 | 来源 |
| --- | --- |
| 渠道 / 工作流 / 模型 / 清晰度 / 生成音频 / 水印 | 源节点 metadata（`buildGenerationConfig`），缺失才回落全局 |
| 画面比例 | 节点显式选过的 `size`；**没选过则跟随参考视频方向**，档位取 0.5M |
| 秒数 | 段长本身，夹到**本次配置**对应的能力区间（`segmentLimitsFor`） |

两条值得记住的理由：

- **画面比例不能回落全局**。分段产物要拼回原片，画幅必须跟原片一致；竖屏段拼进
  横屏片，两边画幅对不上，交付物直接报废。所以没有显式选择时宁可"跟着参考片走"。
- **区间判定要跟着节点走**。用户在节点上换了渠道/工作流，单段能吃多长就变了；
  还按全局那份判，会出现"规划成 6 秒的段，换了 MiniMax 之后每段都不合规"。

另外两处跟着改：

- 段节点 metadata 里记下 `model` / `size` / `vquality`，**单段重试按同一套规格重来**。
  重试出来画幅一变，这段就拼不回成片。
- 弹窗右栏顶部常驻「输出规格」（工作流 / 画面比例 / 单段时长）。参数是否生效，
  用户原来只能从结果反推 —— 摆出来，点生成之前就能核对。

## 8. 段节点：把"这一段吃了什么"写进节点

段节点的参考是**运行时构造**的：从原片切出来的一段视频，加上按顺序拼的参考图集
（勾选的角色图 + 从原片抽的首尾帧）。它们都不体现为画布连线 —— 段节点上只有一条
`lineage` 连线指向源片。结果是用户点开一段，只能看到画面和一句提示词，
既无法核对"模型到底喂了谁、喂了哪几张"，也没法判断改提示词重跑有没有意义。

现在这些信息全部落到 `videoSegment` 里（见 2.1），节点与本地面板一起把它们摊开。

### 8.1 记什么，为什么

| 字段 | 为什么必须记 |
| --- | --- |
| `castNodeIds` + `castSnapshot` | 前者用于重跑（要真图片才能喂），后者是"当初喂了哪几张"的快照 —— 角色节点被删后仍说得清 |
| `anchor.headFrameMs` / `tailFrameMs` | **实际抽帧点**，不是区间边界。只有真的抽了帧才有值：角色替换不送首尾帧，这里就是空的，面板据此判断该不该显示那一行 |
| `referenceClip` | 参考片段节点 id + 地址。节点删了也能播、能追溯 |
| `promptSource` | 这段用的是段级要求还是整批公共提示词。不记的话"我改的到底影响谁"永远说不清 |

抽帧点由 `segmentAnchorTimes()` 统一产出，预铺时写进节点的值与真正抽帧时用的值
必须是同一个函数算的 —— 否则节点上标的首尾帧和模型吃进去的不是同一张，
"事后核对"这件事本身就失去意义。反过来，**不抽帧时要把这两个字段显式清成 `undefined`**：
留着上一次的值，面板会显示"首帧 00:10.0"而模型其实一张都没收到。

### 8.2 面板：参考按模型看到的顺序排

`components/canvas/canvas-video-segment-reference.tsx`。段节点不再显示通用参考栏
（那里的连线参考根本不会进入分段生成，显示出来是误导），改成分段参考清单：

```
参考片段  [首帧缩略]  00:10.0–00:18.0 · 8.0s
角色图    图1 [头像] 图2 [头像]        ← 顺序 = ref_image_01..0N
规格      海螺 全能参考 · 960×544 · 8.0s
提示词    沿用整批的公共提示词
```

角色图下面固定一句"人物外观只来自这几张角色图，参考视频负责动作、镜头与场景，
不再额外送原片首尾帧"——这正是用户最会怀疑的地方。

首尾帧那一行只在两种情况下出现，措辞不同：

- **局部重绘**：正常显示抽帧点 + "只用来钉住接缝，别在提示词里当角色描述"；
- **旧批次**（这一轮之前生成的段，当时无差别送了帧）：标注「旧批次」并说明
  "那两帧里是原人物，重跑一次就会改用纯角色图参考"。

节点本体右上角只放一个 `参考 N 图` 的徽章，计数 = 角色图数（+2 仅当真有首尾帧）。

### 8.3 重跑：段节点的"生成"必须走分段链路

`handleGenerateNode` 开头对 `videoSegment` 节点做了拦截，改走 `handleRetryVideoSegment`。

不拦的后果很具体：通用视频生成只认连线里的参考，段节点上那条 `lineage` 不是参考，
所以它会拿一句提示词去凭空生成一条全新视频 —— 没有参考视频、没有角色图、
画幅按全局猜。用户改完提示词点"生成"，拿到的东西跟这一段毫无关系，
却以为重跑成功了。

重跑后必须重新拼成片，否则等于白跑（段换了画面、成片还是旧的）。`recomposeVideoCut`
按成片节点记下的 `partNodeIds` 把每一段取回来重拼，**就地更新同一个成片节点**。
为此 `videoComposite` 里补记了 `mode` / `keepAudio` / `endAtCut` / `durationMs` ——
这几项只存在于当时的提交参数里，不记就只能猜（猜错的表现是音画不同步、接缝突然发虚）。

两条边界：

- 没有成片时**不**自动合成。没拼过说明这批还没跑完，凭空造一个成片会让人误以为整片好了。
- 角色图全部不可用时**拦住重跑**而不是继续。跑出来的会是"原人物原样回来"的一段，
  看着成功、拼进成片才发现白跑。显式空数组是有效语义（这段不换人），不拦。
